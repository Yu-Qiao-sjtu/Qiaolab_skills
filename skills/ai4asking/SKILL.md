# 有依据的追问

## 职责
把已有回答或论证中最影响判断的缺口转成可回答、可验证的追问。

## 何时使用
- 正例：这段回答说相关性证明了因果关系，帮我找出关键假设并提出追问。
- 反例：把这段文字里的错别字改掉。

## 输入
待审视的原文或明确主张；可选：决策背景、用户已知事实、期望审查深度。

## 交付物
按重要性排列的追问、各问题针对的原文主张与理由，以及需要补充的证据。 默认在对话中交付；只有用户要求文件时，才写入其指定的项目路径，未指定文件名时使用项目内清晰命名的 Markdown 文件并报告路径。

## 不适用范围
不自动接管代码修改、翻译或排版任务；不把未查证的主张判为已证伪，不要求每次回答都做哲学审查。

## 依赖与能力边界
必需：能理解中文的文本模型，以及可读取的输入材料。材料在文件中时需要 Wisp 可用的 `read` 或等效读取工具。无必需 MCP、Python/R 包、CLI、网络或特定操作系统。

可选：用户要求文件时使用可用的 `write` 工具；否则在对话中交付。缺少必需材料或工具时说明具体缺项并暂停依赖它的步骤，其余可独立完成的部分可继续。

## 工作流程
1. 读取 [追问方法与示例](references/methods.md)，按问题需要选择事实、推理或假设层，不必每次运行全部层级。
2. 引用具体主张，标明已知、缺失与推断；优先处理会改变结论的缺口。
3. 为每个关键问题说明什么材料或对照能回答它。原文已经充分支持的部分不反复质疑。

## 权限与完成检查
技能加载只提供说明，不自动执行脚本、安装依赖或授权操作。默认只读取任务相关材料；文件写入遵循用户当前请求与宿主审批。已有明确授权不重复询问；未回答的问题不是授权。不联网检索、上传、发送消息或调用外部服务来补齐证据。

如果生成文件，确认文件真实存在、可读取、内容完整，再报告路径。分别说明材料核对、格式检查、图像判读和实际计算哪些完成、哪些未做；不得把格式通过或访谈类比当作科学有效性证明。安装整个目录并按包内相对路径读取参考材料；没有运行时侧载脚本。
